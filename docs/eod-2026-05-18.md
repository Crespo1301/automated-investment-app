## Finding — API server is serving stale config

`/api/autopilot/status` (and therefore the dashboard) reports
`entry_execution_enabled: true`. The autopilot loop's heartbeats report
`false`, and the loop logged `entry_execution_locked` on all 284 ticks
today. **The loop — the process that actually places trades — is correct.
Entries are off. Nothing traded wrong.**

Cause: the API server (uvicorn) started 10:45 and loaded `apps/api/.env`
*before* the 12:40 edit; the autopilot loop started 13:12, *after* it. Each
process loads `.env` once at startup (pydantic-settings, no live reload).
Fix: restart the API server — see the May 19 plan. The autopilot loop
already has current config and does **not** need a restart.

## Decision — entries stay OFF for the May 19 session

The operator delegated the entries call to Claude ("treat it as your own
money, grow it"). Decision: **do not flip unattended entries on for
May 19.** Reasoning:

- You don't arm a system the morning after finding its status panel
  unreliable. Restart the API first, verify the dashboard reads honestly,
  then decide.
- The entry path has not run once under the current post-cleanup config
  (`pipeline_runs: 0` today). Its first live entry must be attended, not an
  overnight env flip.
- Fractional positions get no broker OCO; protection is a single
  app-managed loop process. Acceptable for babysitting 5 existing lots —
  arming new entries multiplies what depends on that one process.

This is step 1 of an arming ramp, not an indefinite hold. Growth path below.
